# Security Policy

GREM is designed to help users avoid some common C++ safety pitfalls by making its APIs easy to use correctly and hard to use incorrectly, but it cannot guarantee the nonexistence of all potential security vulnerabilities, whether due to language limitations, the risk of discovering latent bugs, design flaws or oversights in the implementation or its dependencies, or the risk of applications using it in an unsafe way. This security policy describes how the project tries to mitigate the risks of these potential vulnerabilities.

> GREM is provided "as is" without warranty of any kind (see [LICENSE](LICENSE)). GREM also depends on some external libraries that have their own separate licenses and security policies. See the respecitve dependencies' external repositories linked under **Dependencies** in [README.md](README.md) for more information.

## Threat model

GREM is primarily intended for non-safety-critical applications, such as video game clients, game developer tooling and game servers, running on a trusted/sandboxed host (e.g. virtual machine or WebAssembly) or a client PC behind a properly configured firewall. Like any C/C++ library, it requires a thorough understanding of the C++ memory model, object lifetimes, undefined behavior, etc. to be used safely and robustly at scale in large/complex applications.

Low-level systems programming languages, like C++, always come with a general risk of exploits when used unsafely. For example:

- Buffer overruns caused by manually constructing a span with invalid extents may lead to information leakage.
- Arbitrary code execution may be made available to attackers due to a use-after-free caused by accidentally returning a reference to a local variable.
- Unknowingly invoking undefined behavior in reachable code may lead the compiler to make optimizations that reorder or remove entire functions and make the program behave in unexpected ways.
- Depending on the platform and system configuration, dynamic memory allocations or exception throwing in memory-constrained scenarios may, in the event of RAM exhaustion or other errors in the host environment, cause abrupt program termination or extreme system slowdown, leading to denial of service.

GREM's threat model assumes that user code is free of such bugs. However, the APIs should, to a reasonable extent, reduce the risk of introducing them accidentally, e.g. by guarding simple preconditions with user-configurable debug assertions whenever checking them would not change the space/time complexity of the function.

## Security guidelines for applications

Applications using GREM should observe the safety-related **API conventions** listed in the [API Reference](https://donutvikingchap.github.io/GREM/index.html) and make sure their code does not invoke undefined behavior of any kind, including all sources of undefined behavior specified or implied by the C++ standard, as well as library-level undefined behavior such as failing assertion checks or violating API contracts.

The project template includes a baseline set of warning flags that all applications should strive to compile with, keeping warnings-as-errors enabled throughout development if possible (since enabling them too late tends to lead to an overwhelming number of warnings to fix). Static analysis tools like `clang-tidy` should also be used when available, e.g. through `clangd` integration in VS Code. False positives generated by these tools should generally be suppressed on a case-by-case basis rather than by disabling checks entirely, though the `.clang-tidy` configuration included with GREM contains some exceptions to this rule that are deemed sensible in the context of game development.

Networked applications should take special care to ensure that any external or untrusted input is properly length-limited and sanitized before being used in any API with preconditions, and should generally **avoid** doing any of the following if possible:

- Opening externally provided filepaths.
- Loading complex resources (image files, models, etc.) fetched from external sources.
- Parsing externally provided data that could potentially have a complex recursive structure (e.g. JSON or XML without a short length limit).
- Storing data in hash-based containers where the keys are externally provided (unless the risk of O(n) lookup due to crafted hash collisions is acceptable).

To reduce their attack surface further, applications acting as servers should also try to limit their use of client-focused modules such as `audio` and `graphics` as much as possible, ideally by not including/invoking them at all unless required.

It is also recommended to use a checked assertions mode, even in release builds, such as `GREM_USE_RELEASE_ASSERTIONS=ON` with `GREM_RELEASE_ASSERTIONS_FAST_FAIL=ON`, whenever the benefit of turning some potential high-severity exploits into mere denial of service outweighs the (small) performance impact.

## Reporting security bugs

If you have found a security vulnerability in GREM, please report it through the GitHub [Security Advisories](https://github.com/DonutVikingChap/GREM/security/advisories) page, bearing in mind the limitations and guidelines mentioned above, and noting the **No-AI policy** in [README.md](README.md#no-ai-policy).

Bugs found in the following areas are particularly relevant:

- Parsing code in `core/formats` (JSON, XML, deflate, etc.).
- Container implementations in `core/data`.
- Anything in the `networking` module.

> [!NOTE]
> GREM is currently maintained by volunteers in their spare time. As such, there is unfortunately no guarantee that official fixes for vulnerabilities will be implemented and/or released in a timely manner. There is also no compensation for reporting bugs. If this poses an unacceptable risk to your project, GREM may not be a good fit for it at this stage.
